
AI VIDEO EDITOR — EVERYTHING DUMP
=================================

PURPOSE
-------
This file is the consolidated project-memory dump for the personal AI video editor project developed across the conversation history and the retained project context.

IMPORTANT SCOPE NOTE
--------------------
This is a reconstruction of the project's complete known design context from the conversation and remembered project state. It is not a byte-for-byte transcript of every chat message, and it intentionally excludes unrelated private/account/location information. It preserves the project's ideas, decisions, discarded approaches, constraints, architecture, research conclusions, open questions, and implementation details.

The project is a personal, experimental, garage/basement-scale AI video editing system. It is not intended as a SaaS product or enterprise platform. It should be practical, surprisingly capable, and built around free/low-cost compute where possible.

================================================================================
1. THE CORE IDEA
================================================================================

The AI video editor is an agent that takes a script and media, performs real editing operations, renders short sections, watches what it actually produced, compares reality against the intended script, fixes mistakes, and continues until the whole video is complete.

The fundamental loop is:

    READ SCRIPT
        ->
    PLAN/EDIT A SHORT SEGMENT
        ->
    RENDER THE SEGMENT
        ->
    WATCH / INSPECT THE RENDERED RESULT
        ->
    TRANSCRIBE / UNDERSTAND WHAT ACTUALLY HAPPENED
        ->
    COMPARE INTENDED VS ACTUAL
        ->
    DETECT DISCREPANCIES
        ->
    FIX THE TIMELINE / EDIT
        ->
    CONTINUE

The latest preferred chunk size is roughly 8 seconds of video.

The next 8-second segment should have about 3 seconds of immediately preceding rendered context so continuity is maintained.

The AI is explicitly NOT supposed to blindly trust its own plan.

The central philosophy is:

    PLAN -> CREATE -> OBSERVE -> COMPARE -> CORRECT -> CONTINUE

This is the heart of the project.

The system should be able to stop and ask the user for help when it genuinely cannot resolve something rather than inventing a confident answer or silently producing bad video.


================================================================================
2. WHY THE DESIGN EVOLVED
================================================================================

The project started from a more GUI-oriented concept where an AI could operate a video editor by using computer-use / keyboard / mouse actions.

That approach was reconsidered.

The important realization was:

A GUI viewport is expensive and unnecessary for the normal operating loop.

The editor is rendering every short segment anyway. The agent does not need to continuously stare at an interactive viewport like a human editor would. If the editor exposes a rich project/timeline API, deterministic timeline operations can be issued directly.

This led to the API-FIRST design.

The revised principle is:

    AI
     |
     v
    Editor API / MCP
     |
     v
    Actual NLE project + timeline
     |
     v
    Render
     |
     v
    AI observes rendered result

The GUI is not the main control surface anymore.

Computer-use can still exist as a fallback/debug mechanism for unusual unsupported operations, dialogs, or emergency interaction, but it is not intended to be the primary control path.

The project specifically does NOT want FFmpeg to be treated as the entire editor abstraction.

FFmpeg can still be part of the underlying media/rendering pipeline where appropriate, but the AI should control a real editor/project representation with real editing semantics.

Desired semantics include clips, tracks, trims, splits, transitions, transforms, keyframes, audio, captions, effects, markers, project state, and rendering.

================================================================================
4. CURRENT PRIMARY EDITOR: VELORN
================================================================================

The current selected editor target is VELORN.

Other candidates were investigated, but Velorn became the preferred target because it is designed around agent/editor integration and exposes an MCP layer.

Key project-level research findings about Velorn from the time it was investigated:

- It is a real non-linear editor / video editing system.
- It has an MCP layer intended for agent control.
- Its MCP system exposes a large tool surface (documentation discussed roughly 125 MCP tools).
- It can expose the current project and active timeline.
- It includes asset/timeline editing operations.
- It has caption-related operations.
- It has export/render operations.
- It has visual inspection/workflow/generation related capabilities.
- It is open source / GPL-3.0.
- It was pre-1.0 and actively developing when checked, so API stability should be treated as an engineering risk.
- A late-September 2026 release discussed hardware-assisted background media preparation using NVIDIA NVENC and Apple VideoToolbox, with CPU fallback.

The specific repository and release numbers checked at that time were approximately:
- ~494 GitHub stars
- ~67 forks
- ~21 open issues
- ~6 open PRs
- v0.3.36
- ~421 commits

Those numbers are historical snapshots, not permanent facts.

The important reason for choosing Velorn is architecture:
it offers a real editor/project model while also exposing an MCP path designed for an AI agent.

The project should keep a mature alternative as a fallback/benchmark.


================================================================================
5. ALTERNATIVE EDITOR RESEARCH
================================================================================

SHOTCUT
-------
Shotcut was investigated as a strong mature fallback.

Important findings:
- Free and open source.
- Multitrack timeline model.
- QML API exposes internal editor/project state.
- Can manipulate producers/clips and timeline structures.
- Supports markers, subtitles, filters, keyframes, fades, speed, transitions, etc.
- Mature enough to be a realistic reference implementation / fallback.

Shotcut is important because it demonstrates that a mature desktop NLE can expose a meaningful internal model even if the API is not as agent-first as Velorn.

BLENDER VSE
----------
Blender's Video Sequence Editor was investigated as the highly programmable alternative.

Strengths:
- Python API.
- Headless operation is possible.
- Rich sequencer data model.
- Programmatic strip creation, movement, splitting, retiming, transitions, effects, text, audio and keyframes.
- Can render without requiring a human to sit in front of a viewport.

Weakness:
It is a general 3D application rather than a conventional NLE, so the editing workflow and user-facing semantics are different.

WEFTCUT
-------
An AI-native editor with MCP-style operations was found.
Discussed operation categories included placing, trimming, splitting, restyling, keyframing, grouping, captioning, mixing and checkpoints.
Interesting, but early.

KINEWRIGHT
----------
Another agentic editor concept with MCP-driven operations.
Interesting but early in development.

ORCCUT
-------
Discussed as an MCP-oriented editor exposing roughly dozens of timeline operations including trim, split, move, resize, transforms, keyframes, transitions and color operations.
Very young.

FRONTSTAGE
----------
Investigated as an MCP/editor stack with multi-track editing, ripple editing, razor/splitting, linked audio/video, keyframes, transforms, crop, volume, color, transitions, captions, transcription and export.

KDENLIVE
--------
Interesting because of its MLT-backed project representation and third-party API experiments.
The project representation itself can be manipulated, but the official scripting/API situation was less straightforward than the desired agent-first experience.

DAVINCI RESOLVE
---------------
Excellent editor, but the official scripting/automation setup was tied to Studio in the relevant context, which conflicts with the project's zero-cost/free-compute goal.

Conclusion from the search:
Velorn is the current primary target.
Shotcut is the mature fallback/benchmark.
Blender VSE is the programmable alternative if the project needs a nuclear-option programmable editor.

7. KAGGLE + COLAB SPLIT
================================================================================

The working idea is:

KAGGLE:
- Host the AI model.
- Train/fine-tune the model.
- Perform inference / analysis.
- Potentially perform video understanding workloads.

COLAB:
- Host Velorn and its rendering environment.
- Run the editor/project.
- Render the short video sections.

CONNECTIVITY:
- MCP server between the agent and editor.
- Cloudflare tunnel can expose the editor-side MCP service where needed.

The key realization is that this does NOT require a live GUI stream.

Only structured commands and relatively small review outputs need to cross the connection:
- MCP tool calls
- project/timeline state
- metadata
- short rendered sections / sampled frames
- transcripts / analysis information

Latency therefore matters less than it would in interactive remote desktop control.

The real practical risks to test are:
- free-tier runtime limits
- session resets
- inbound tunnel reliability
- whether the editor/desktop environment runs correctly in the cloud runtime
- GPU driver availability
- hardware encoding availability
- storage persistence
- network throughput when actual video chunks are transferred

The architecture should therefore be checkpointed and restartable.


================================================================================
8. TARGET GPU SETUP
================================================================================

A target setup discussed was:

    2 x NVIDIA Tesla T4

Each T4 is 16 GB VRAM.

Important:
Two T4s are NOT automatically one unified 32 GB VRAM pool.

A sensible division is:

T4 #1:
- AI inference
- video understanding
- model workload

T4 #2:
- Velorn rendering
- video processing
- potentially another model or secondary workload

The exact allocation may change depending on runtime behavior.

The project target is 720p30.

720p30 means:
- resolution: 1280 x 720
- frame rate: 30 fps
- 8-second segment: 240 frames

720p30 is a sensible prototype target.

The editor's rendering of already existing/generative media is generally far less expensive than generating every pixel of a video from scratch.

9. MODEL DIRECTION
================================================================================

The currently stated model choice is:

    SmolVLM 2.2B

The goal is to fine-tune an actual multimodal/video-capable model rather than build the editor around text-only prompting.

The model should be able to consume some combination of:

- script text
- visual frames
- audio/transcript information
- current timeline/project state
- available assets
- tool schemas
- prior decisions
- previous rendered context

and then produce:

- structured reasoning/state
- editing actions / tool calls
- critiques
- corrections

The model does not need spoken voice output for the sense of “speaking” discussed in the project. “Speaking” in this context means producing meaningful structured actions, decisions, and tool calls as a multimodal agent.

10. MODEL-SIZE / TRAINING FEASIBILITY THINKING
================================================================================

Several models were considered during exploration:

- MiniCPM-V 4.0 (~4.1B)
- InternVL2.5-4B (~3.7B)
- Qwen2.5-VL-3B (~3.8B)
- InternVL2.5-2B (~2B)
- MiniCPM-V 4.6 (~1.3B)
- InternVL2.5-1B (~1B)
- SmolVLM 2.2B (current stated target)

The constraint is that large models are harder to fine-tune on free hardware.

The practical direction is parameter-efficient fine-tuning and careful sequence/frame budgeting rather than attempting a giant full-parameter training run.

The exact training method, quantization, context length, frame budget, batch size, gradient accumulation, and checkpointing should be tested empirically on the actual available GPU environment.

An important distinction established in the project:

Fine-tuning teaches behavior.

These are different systems.

FINE-TUNING SHOULD TEACH:
- tool usage
- Velorn/editor knowledge
- editing concepts
- style patterns
- raw footage interpretation
- self-critique behavior

- project decisions
- constraints

- unresolved questions

The model should not need to rediscover all project facts every few seconds.

14. THE 8-SECOND EDIT / RENDER LOOP
================================================================================

The latest core local loop is around 8 seconds.

For each segment:

1. Read the relevant script section.
2. Read persistent project context.
3. Read available timeline state.
4. Read the relevant raw media/assets.
5. Read approximately 3 seconds of preceding rendered context.
6. Decide what should happen.
7. Apply edits through Velorn/MCP.
8. Render the ~8-second result.
9. Sample/inspect the result.
10. Transcribe/understand the audio.
11. Determine what actually happened.
12. Compare the actual result against the intended result.
13. Record discrepancies.
14. Apply corrections if necessary.
15. Accept the segment.
16. Move to the next section.

The AI should be capable of multiple correction passes.

The project should not assume “first render = final render.”

================================================================================
16. FRAME SAMPLING / OBSERVATION
================================================================================

Several sampling ideas were explored.

One major idea was around:
    1 frame every 0.5 seconds
which is 2 FPS.

For a long video this drastically reduces the raw number of visual observations compared with processing every frame.

Earlier experiments also considered:
- 5-second chunks
- 20 frames per 5 seconds
which corresponds to 4 FPS for that local window.

The later architecture settled on:
- ~8-second generation/render chunk
- ~3 seconds of previous rendered context
- ~2 FPS as a useful baseline observation rate
- denser sampling where necessary

The model should not be forced to use a single fixed frame rate for every situation.

Examples where denser sampling may be useful:
- fast motion
- rapid cuts
- small visual text
- a critical transition
- visual effects
- lip-synced events
- a short visual joke

The observation pipeline should be adaptive if possible.

17. 5-SECOND / MICRO / LOCAL / MACRO CONCEPT
================================================================================

An earlier architecture used three conceptual layers.

MICRO
-----
Approximately 0.5-second observations for event awareness.

LOCAL
-----
Approximately 5-second analysis/editing windows.

MACRO
-----
Full-video contextual review.

MICRO:
    What is happening right now?

LOCAL:
    What should this short section do?

    Does the whole video make sense together?

The project should NOT treat chunks as fully independent.

Overlap/context is required because:
- jokes can span boundaries
- dialogue can span boundaries
- music can span boundaries

================================================================================
19. PLAN VS REALITY STATE
================================================================================

A simple persistent state format was designed conceptually:

    intended:
        what the script / plan says should happen

    actual:
        what the rendered result actually contains

    discrepancy:
        what went wrong / what is missing / what is weak

    correction:
        what the next edit should change

Example:

    intended:
        punchline happens at ~3.0s and reaction cut immediately follows

    actual:
        setup shot continues until ~4.2s and reaction appears too late

    discrepancy:
        pacing is late by ~1.2s

    correction:
        trim setup, move reaction earlier, rerender

The important property is that the model explicitly reasons from observed reality rather than hallucinating that its edit succeeded.

UNPROCESSED ASSETS RULES:
- never delete
- never rename
- never move
- never modify
- only scan
- only read
- only hash
- only copy

================================================================================
28. COPY / PROCESS WORKFLOW
================================================================================

When processing an unprocessed asset:

1. Scan the source.
2. Collect metadata.
3. Detect duplicates.
4. Copy the source into processed_assets.
5. Verify the copy.
6. Register it in library.json.
7. Rename only the processed copy if requested.
8. Never touch the original.

If verification fails:
- rollback the processed copy
- do not corrupt the source
- record the failure

35. EDITING STYLE VS CONTENT
================================================================================

The style system should separate:

CONTENT:
    what is being said / shown

STYLE:
    how it should be edited

This is important because the reference videos are not necessarily about the same subject matter as the generated video.

The model should learn something like:

    "When a moment of this type happens, this is the editing behavior I tend to use."

rather than:

    "Always copy this exact clip."

================================================================================
36. TIMELINE STATE IS AN INPUT
================================================================================

The model must be able to inspect the actual project state.

Useful timeline information includes:
- tracks
- clip IDs
- start time
- end time
- durations
- source asset
- effects
- transitions
- transforms
- keyframes
- volume
- captions
- markers
- active timeline
- export settings

The editor state prevents the agent from making contradictory assumptions.

Example:
If it thinks a clip ends at 4 seconds but the timeline says it ends at 4.8 seconds, timeline state wins.


================================================================================
37. VERSIONING / CHECKPOINTING
================================================================================

Because the AI is autonomous, every important local operation should be recoverable.

Useful checkpoints:
- before an edit
- after a successful render
- after correction
- after major macro changes

The project should be able to:
- roll back a bad segment
- compare timeline versions
- resume after cloud runtime loss
- restore a previous good state

This is especially important on free cloud environments where sessions can disappear.


================================================================================
38. 30-HOUR RUNTIME IDEA
================================================================================

An idea discussed was allowing approximately 30 hours of autonomous runtime per finished video as an upper ceiling.

This could be plenty for a 10-minute video because the system may spend substantial time:
- rendering
- observing
- correcting
- doing macro review
- retrying difficult segments

However, 30 hours should be treated as a ceiling, not a requirement.

The preferred stopping condition is quality / acceptance criteria:
    stop when the video passes the checks,
not:
    keep running until the timer expires.


================================================================================
39. 10-MINUTE SOURCE VIDEO EXAMPLE
================================================================================

A representative thought experiment used videos around 10 minutes long.

At 2 observations per second:

    10 minutes * 60 seconds * 2 FPS = ~1200 observations

This is much more manageable than processing every video frame.

The number of observations can still increase selectively around high-motion/high-importance sections.

The working dataset target discussed was approximately 50 reference videos.

They should ideally be diverse enough to expose:
- fast and slow pacing
- dialogue
- jokes
- reactions
- sound effects
- captions
- music
- visual edits
- different scene structures

The point is to teach editing behavior rather than memorize exact content.

================================================================================
42. EVIDENCE / CONFIDENCE
================================================================================

The system should distinguish:
- directly observed facts
- strong inferences
- uncertain guesses

For example:

DIRECT:
    "The transcript says X."

OBSERVED:
    "The shot contains a red object at approximately 2.5 seconds."

INFERRED:
    "This appears to be the moment intended for the joke."

UNCERTAIN:
    "The user may want a reaction cut here."

This helps prevent the AI from turning uncertainty into false certainty.


================================================================================
43. ASK-THE-USER FALLBACK
================================================================================

The agent should have a controlled way to ask the user for help.

Examples:
- required asset cannot be found
- source is corrupted
- two plausible edits conflict
- a script instruction is ambiguous
- an editor operation is unsupported
- a render repeatedly fails
- the model cannot determine whether a visual event is intentional

The fallback should be:
    "Here is what I know, here is what I tried, here is exactly what is ambiguous."

Not:
    hallucinate a resolution.


================================================================================
44. MCP IS THE TOOL BUS
================================================================================

MCP is the preferred connection between the model and the editor.

The model should not have to generate arbitrary shell commands for every edit.

Instead it should produce structured tool calls corresponding to actual editor operations.

Conceptually:

    tool:
        trim_clip
    args:
        clip_id
        new_in
        new_out

or:

    tool:
        add_transition
    args:
        track
        clip_a
        clip_b
        transition_type
        duration

The exact Velorn schema should be learned from its current MCP tool definitions.


================================================================================
45. COMPUTER-USE FALLBACK
================================================================================

GUI control is not dead; it is just no longer the primary architecture.

Possible fallback uses:
- an unsupported editor dialog
- a one-off export setting
- visual debugging
- checking unexpected UI state
- emergency setup
- recovery when an API operation is temporarily unavailable

Normal editing should be:
    API/MCP first.


================================================================================
46. WHY NOT LIVE VIEWPORT CONTROL
================================================================================

Reasons:

1. Memory:
   a live editor viewport adds unnecessary graphical overhead.

2. Compute:
   the agent would waste compute interpreting UI elements rather than timeline state.

3. Reliability:
   deterministic API operations are more reliable than screen-coordinate actions.

4. Debuggability:
   structured project state can be inspected.

5. Reproducibility:
   the same tool call can recreate an edit.

6. Cloud suitability:
   headless/API-first workflows fit cloud compute much better.

7. Render loop already exists:
   the AI gets a real video result after it edits.


================================================================================
47. WHY NOT FFmpeg AS THE EDITOR
================================================================================

FFmpeg is excellent infrastructure for media operations, but the desired abstraction is richer.

The AI wants to think in:
- clips
- tracks
- edits
- transitions
- keyframes
- captions
- assets
- timeline state

The project therefore prefers:
    real NLE/project model
over:
    raw command-line filter graphs as the agent's primary mental model.

FFmpeg may still live underneath the editor/render stack.


================================================================================
48. CLOUD / FREE-COMPUTE DESIGN PHILOSOPHY
================================================================================

The project is intentionally designed around free or near-free compute wherever possible.

Consequences:
- checkpoint everything
- avoid long uninterrupted assumptions
- keep state external to ephemeral sessions
- minimize unnecessary video transfer
- use efficient frame sampling
- use parameter-efficient training
- tolerate restarts
- keep the editor and model separable


================================================================================
49. NETWORKING PHILOSOPHY
================================================================================

The proposed split is not dependent on a low-latency remote desktop.

The traffic is mostly:
- structured MCP commands
- timeline state
- metadata
- selected frames
- short rendered segments
- transcripts

Therefore moderate WAN latency can be acceptable.

Bandwidth matters more when moving large raw video files.

Preferred strategy:
- keep source media near the editor when possible
- send only necessary observations to the model
- render short review clips
- avoid streaming an entire editor UI


================================================================================
50. RENDERED OUTPUT IS GROUND TRUTH FOR REVIEW
================================================================================

One of the strongest principles in the project is:

Do not critique the plan.
Critique what was actually rendered.

The plan is hypothetical.
The render is evidence.

That is why the pipeline is:

    plan
      ->
    edit
      ->
    render
      ->
    observe
      ->
    compare

52. PROJECT PHILOSOPHY
================================================================================

The goal is not:

"Make an AI that can call an NLE API."

The actual goal is:

"Make an AI that can repeatedly make editing decisions, observe whether those decisions worked, and improve the edit until the result satisfies the script and style."

The editor is a body/tool environment.

The model is the decision-maker.

The render is the experiment.

The observation is the measurement.

The correction is the learning/action loop.

53. IMPORTANT ENGINEERING DISTINCTION: PLAN VS STATE
================================================================================

There are at least four categories of project knowledge:

A. AUTHORITATIVE INPUT
- script
- source media
- user requirements
- explicit constraints

B. OBSERVED STATE
- current timeline
- rendered output
- transcript
- frame observations

C. DERIVED STATE
- likely beat boundaries
- inferred continuity
- suggested cut points

D. AGENT DECISIONS
- selected clip
- chosen effect
- correction plan

These should not be mixed together.

The model should know whether a fact came from the script, timeline, render, or its own inference.

59. EDIT ACCEPTANCE
================================================================================

A local chunk should eventually be accepted only when checks pass.

Possible acceptance requirements:
- script beat is present
- intended timing is approximately satisfied
- audio is coherent
- continuity is acceptable
- no obvious render errors
- style is acceptable
- no missing required asset
- no unexplained discrepancy remains

Not every chunk needs to be perfect in isolation, because the macro pass exists.


================================================================================
60. RETRIES
================================================================================

The system should maintain a retry budget.

For example:
- retry render if renderer fails
- retry edit if a measurable discrepancy exists
- escalate if repeated corrections do not converge

A recurring failure should produce a meaningful diagnostic record.

Never allow an infinite loop where the model keeps making the same correction.


================================================================================
61. DIFFERENT FAILURE CLASSES
================================================================================

FAILURE TYPE A:
Editor/tool failure.
Example:
tool call rejected.

FAILURE TYPE B:
Render failure.
Example:
export crashes.

FAILURE TYPE C:
Observation failure.
Example:
model cannot interpret a critical frame.

FAILURE TYPE D:
Script ambiguity.
Example:
two interpretations are plausible.

FAILURE TYPE E:
Creative mismatch.
The output is technically correct but stylistically weak.

FAILURE TYPE F:
Non-convergence.
The system tries several corrections and the result does not improve.

Each category should be handled differently.


================================================================================
62. MODEL SHOULD NOT BECOME “BLIND TOOL CALLER”
================================================================================

A successful system is not just:

    script -> tool call -> next tool call

It should maintain a loop in which it checks whether the world changed as expected.

The model should have an internal discipline:

    "I issued this command.
     What should it have changed?
     Did the render actually reflect that?
     If not, why?"

63. TOOL-SCHEMA LEARNING
================================================================================

The model should learn:
- tool name
- purpose
- required arguments
- optional arguments
- return structure
- failure cases
- state dependencies

But the agent runtime should still validate tool arguments.

Do not rely on fine-tuning alone to protect against malformed tool calls.

81. GLOSSARY
================================================================================

NLE:
    Non-linear editor.

MCP:
    Model Context Protocol / structured tool interface connecting the agent to external tools.

LOCAL CHUNK:
    A short editing/render window, currently ~8 seconds.

PREVIOUS CONTEXT:
    Approximately 3 seconds of already-rendered video supplied to the next local edit for continuity.

MICRO:
    Fine-grained event observations, historically around 0.5 second intervals.

MACRO:
    Whole-video contextual review.

PLAN VS REALITY:
    Comparison between intended content and observed rendered content.

ASSET LIBRARY:
    Structured collection of reusable images, audio, video and other media with metadata.

PROCESSED ASSET:
    Canonical working copy that is safe for downstream use.

UNPROCESSED ASSET:
    Original source material which the library must never modify.

CHECKPOINT:
    Recoverable project state after a known-good operation.

SELF-CRITIQUE:
    Explicit observation and correction of the agent's own output.
